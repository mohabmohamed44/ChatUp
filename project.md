  # ChatUp Developer Assessment

  ## 1. Purpose

  Build a complete, production-minded, real-time messaging web application named ChatUp.

  The product should feel inspired by modern messaging applications such as WhatsApp,
  while using its own design, branding, components, and implementation. Do not copy
  WhatsApp’s logo, assets, or interface exactly.

  This assessment evaluates your ability to:

  - Design a polished, usable product.
  - Build and integrate a complete frontend and backend.
  - Implement real-time communication using sockets.
  - Handle text, image, and voice messages.
  - Design and validate a system supporting at least 100 concurrent users.
  - Test, deploy, monitor, and document an application.
  - Use AI tools critically and responsibly.
  - Explain technical decisions and trade-offs.

  Production-minded means demonstrating sound engineering practices and acknowledging
  limitations. It does not mean claiming production readiness without evidence.

  ## 2. Access and Safety Boundaries

  Build ChatUp in an isolated development or assessment environment.

  This assessment does not require or authorize access to ChaiTalk production systems,
  production secrets, customer information, or billing administration.

  Use synthetic users, generated conversations, and test media. Never copy customer data
  into the assessment environment.

  Use only explicitly provided assessment credentials or your own authorized development
  resources. Do not create paid resources or incur charges without prior authorization.

  Keep secrets out of source control, screenshots, documentation, logs, and AI prompts.
  Provide an .env.example containing placeholders only.

  ## 3. Product Summary

  ChatUp is a responsive, browser-based messaging application.

  Users must be able to:

  - Create an account, sign in, and sign out.
  - View and edit basic profile information.
  - Find another user and start a direct conversation.
  - View their conversations and unread message counts.
  - Exchange text messages in real time.
  - Upload and send image messages.
  - Record and send voice messages.
  - View online and offline states.
  - See when another user is typing.
  - See message delivery and read status.
  - Use the application comfortably on desktop and mobile browsers.

  The required scope is one-to-one messaging. Group conversations, calls, and other
  extensions are optional.

  You may use established libraries for authentication, validation, accessibility

  ## 5. Design and User Experience

  Create a coherent visual identity for ChatUp, including an original wordmark or simple
  logo, color palette, typography, spacing, and component styles.

  Required screens and states include:

  - Sign-up and sign-in.
  - Conversation list.
  - Conversation view.
  - User search or a new-conversation flow.
  - Profile settings.
  - Empty, loading, error, disconnected, and retry states.

  On desktop, users should be able to browse conversations while viewing an active chat.
  On mobile, navigation between the conversation list and active chat should be clear and
  comfortable.

  Provide accessible labels, visible keyboard focus, sufficient contrast, and useful
  validation messages. Core actions must work with a keyboard.

  Long messages, large images, failed uploads, microphone denial, and narrow screens must
  not break the layout.

  ## 6. Accounts and Authentication

  Implement:

  - Registration using a unique email address and password.
  - Secure password hashing.
  - Sign-in and sign-out.
  - Authenticated HTTP requests and socket connections.
  - Session expiration handling.
  - Basic profile editing, including display name and an optional avatar.

  Use secure session handling and document the approach. If using cookies, configure
  their security attributes appropriately and address CSRF where applicable.

  Validate inputs on the server. Rate-limit authentication attempts and avoid exposing
  credentials or session tokens in logs.

  Email verification and password reset are optional, but clearly document their omission
  if not implemented.

  ## 7. Conversations and Message History

  Users must be able to search for another user and start a direct conversation.

  Requirements:

  - Prevent duplicate direct conversations for the same pair of users.
  - Show the latest message preview and timestamp.
  - Show unread counts.
  - Sort conversations by recent activity.
  - Load message history incrementally using pagination.
  - Retain messages after refresh and reauthentication.
  - Restrict conversation access to its participants.

  Do not expose sensitive account information through user search.

  Define consistent ordering for messages, including when multiple messages have the same
  timestamp.

  ## 8. Real-Time Messaging

  Use sockets for real-time message and conversation updates.

  Implement:

  - Authenticated socket connections.
  - Authorized conversation subscriptions or rooms.
  - New-message events.
  - Conversation-list updates.
  - Reconnection behavior.
  - Missed-message recovery.
  - Server acknowledgements.
  - Duplicate prevention for retried sends.

  Persist messages before acknowledging them as successfully sent. Use stable message
  identifiers and an idempotency mechanism so retries do not create duplicate messages.

  The interface should distinguish pending, sent, and failed messages. Failed sends must
  offer a clear retry action.

  Document your event contracts, acknowledgement behavior, ordering strategy, and
  assumptions about delivery guarantees.

  ## 9. Text Messages

  Support multiline plain-text messages.

  Requirements:

  - Preserve intentional line breaks.
  - Define a reasonable maximum message length.
  - Reject empty or whitespace-only messages.
  - Render user content safely.
  - Provide readable timestamps.
  - Keep the message composer usable on mobile.

  Do not interpret arbitrary user input as trusted HTML.

  Optimistic rendering is encouraged, provided the interface reconciles correctly with
  persisted server messages.

  ## 10. Image Messages

  Users must be able to select, preview, upload, and send an image.

  Requirements:

  - Validate file size and supported formats on the server.
  - Check actual file content rather than trusting the filename.
  - Show upload progress or a clear pending state.
  - Handle upload failure and retry.
  - Display images without disrupting the conversation layout.
  - Provide an enlarged image view.
  - Store media outside the application database.

  Restrict media access to authorized conversation participants. Explain your use of
  private storage, signed URLs, or authenticated media delivery.

  Document file limits and handling of abandoned uploads.

  ## 11. Voice Messages

  Users must be able to record, preview, send, and play voice messages.

  Requirements:

  - Request microphone access only when needed.
  - Show recording status and elapsed time.
  - Allow recording cancellation.
  - Provide a preview before sending.
  - Enforce a documented maximum recording duration.
  - Display message duration and playback controls.
  - Handle denied permissions and unsupported browser features.
  - Validate uploaded audio on the server.

  Use browser-supported recording and playback APIs. Document the browsers and audio
  formats you tested.

  Serve the deployed application over HTTPS so microphone access can work in supported
  browsers.

  ## 12. Presence, Typing, and Message Status

  ### Presence

  Display online and offline states using authenticated connection activity.

  Handle multiple tabs or devices sensibly. A user should not appear offline while
  another active connection remains.

  Use a timeout or grace period to avoid rapid status changes during brief network
  interruptions.

  ### Typing

  Show a typing indicator only to the relevant conversation participant.

  Throttle typing events and expire stale indicators automatically. Typing activity does
  not need permanent storage.

  ### Delivery and Read Status

  Define and implement these meanings:

  - Sent: The server has persisted the message.
  - Delivered: At least one recipient client has acknowledged receiving it.
  - Read: The recipient has viewed the message in the active, visible conversation.

  Do not mark a message as read solely because it arrived over a socket. Status
  transitions must remain consistent across reconnects and multiple sessions.

  ## 13. Data Model and API

  Design a relational schema covering:

  - Users.
  - Sessions or refresh tokens, where applicable.
  - Conversations.
  - Conversation participants.
  - Messages.
  - Media attachments.
  - Delivery and read tracking.

  Include appropriate foreign keys, uniqueness constraints, and indexes.

  Explain your message-status model and how it handles multiple devices.

  Provide versioned database migrations and a repeatable seed command using synthetic
  data.

  Document HTTP endpoints and socket events, including authentication, payloads,
  validation, acknowledgements, and error responses.

  ## 14. Security and Privacy

  Implement server-side authorization for every protected HTTP endpoint and socket event.

  Users must not be able to:

  - Read conversations they do not belong to.
  - Subscribe to another conversation by guessing its identifier.
  - Impersonate a message sender.
  - Access another conversation’s private media.
  - Submit delivery or read updates on another user’s behalf.

  Also address:

  - Input validation and output safety.
  - Authentication and message rate limits.
  - Upload restrictions.
  - CORS and socket origin configuration.
  - Secret management.
  - Safe error responses.
  - Dependency vulnerabilities.
  - Logging that avoids passwords, tokens, and message contents.

  Do not claim end-to-end encryption unless you implement and explain it. HTTPS and
  encrypted storage do not constitute end-to-end encryption.

  ## 15. Performance and Concurrency

  Demonstrate support for at least 100 simultaneously connected users under a documented
  workload.

  The load test must include active message sending and receiving, rather than only
  opening idle connections.

  Document:

  - Test infrastructure and application resources.
  - Number of users and conversations.
  - Message size and send rate.
  - Test duration.
  - Connection success and error rates.
  - End-to-end message latency, including p50 and p95.
  - CPU and memory observations.
  - Missing or duplicate messages.
  - Bottlenecks and proposed improvements.

  Include a sustained test of at least 10 minutes after warm-up.

  State performance targets before running the test. Report actual results honestly,
  including failures and limitations.

  Explain how the architecture could scale beyond one backend instance.
